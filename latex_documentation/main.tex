\section{Fine tuning dataset}
    

To fine-tune LLaMA~3~8B for answer generation and provenance explanayion, we construct adataset where each training example is represented as a structured <input,output> pair.
The input consists of a natural language question and its corresponding SQL query, while the output is a JSON object containing both the query answers and their provenance, expressed as witness sets.
Each answer is explicitly paired with a single witness set.

An example of a training instance is reported below:
\begin{Verbatim}
{
  `instruction`: `Return ONLY valid JSON (no extra text).Output MUST be a JSON array. 
  Each array element MUST be an object with EXACTLY these keys:
  - result: an object representing one output tuple
  - provenance: a Why[X] provenance expression for that tuple, where each provenance identifier 
  is a string formatted as ``<table_name>_<row_number>'' (e.g., ``standings_35'').
  The provenance field MUST be a list of lists of provenance identifiers.
  Each inner list contains the provenance identifiers that together produce the result tuple.JSON schema:
  [{``result'': \{...\}, ``provenance'': [[``t1'',``t2''], [``t3''], ...]}, ...]
  Do NOT output SQL, explanations, markdown, or additional keys.If there are no results, return [].`,
  `input`: {
    `question`: `What are the dates and points for each constructor standing, along with their corresponding 
    subsequent standings, for the 28 most recent races?`
  },
  `output`: [
    {
      `result`: {
        `raceid`: `21`,
        `points`: `3`,
        `constructorresultsid`: `38`
      },
      `provenance`: [
        [`constructor_results_38`]
      ]
    }
  ]
}

\end{Verbatim}

\section{Curriculum Learning}
Curriculum learning (CL) is a training strategy that trains a model from easier data to harder data, imitating learning order in human curricula.
In the paper \emph{A Survey on Curriculum Learning}\cite{curriculumsurvey}, training examples are ordered according to an explicit difficulty measure, such as the number of joins, self-joins, and output tuples.
The model is first trained on simpler instances and progressively exposed to more complex queries, allowing it to learn the rigid output format and the semantics of witness sets before handling harder relational patterns.



\begin{algorithm}[H]
\caption{Baby Step Training Scheduler\cite{curriculumsurvey}}
\label{alg:baby_step}
\KwIn{$D$: training dataset; $C$: difficulty measurer}
\KwOut{$M^*$: trained model}
$D' \leftarrow \text{sort}(D, C)$\;
$\{D_1, D_2, ..., D_k\} \leftarrow D'$ such that
$C(d_a) < C(d_b)$, $d_a \in D_i$, $d_b \in D_j$, $\forall i < j$\;
$D_{\text{train}} \leftarrow \emptyset$\;
\For{$s = 1$ \KwTo $k$}{
  $D_{\text{train}} \leftarrow D_{\text{train}} \cup D_s$\;
  \While{not converged for $p$ epochs}{
    train($M$, $D_{\text{train}}$)\;
  }
}
\end{algorithm}

    Each fine-tuning example will be augmented with the full relational context required to answer the query, including all relevant rows and attributes.     Duplicate attributes in the \texttt{SELECT} clause will be removed during query generation to improve query quality and avoid introducing redundant or misleading supervision signals.

    \item \textbf{Model fine-tuning.}  
    Once the datasets are finalized, supervised fine-tuning will be performed to adapt the model to structured query answering with provenance-aware explanations.

    \item \textbf{Model distillation.}  
    After fine-tuning, knowledge distillation techniques will be explored to transfer the acquired capabilities to smaller or more efficient models, improving deployability while preserving performance.

    \item \textbf{Provenance-to-Natural-Language translation.}  
    Finally, we will design and implement a Prov-to-NL translation component aimed at generating faithful and interpretable natural language explanations from structured provenance, improving the transparency and usability of the system.

\section{Observation and limitations}
During a manual inspection of the generated SQL queries, their automatically generated natural language (NL) questions, 
and the corresponding outputs with provenance produced by ProvSQL, several limitations emerged that can directly affect the quality of the fine-tuning dataset.

In our setup, the output of the execution of the SQL queries, together with the provenance, is always correct with respect to the SQL semantics (we are using ProvSQL to generate it). 
However, the NL questions are automatically generated using an LLM and represent the weakest component of the pipeline,
introducing a significant source of noise. This asymmetry is intrinsic to the generation process and reflects a realistic scenario 
in which user queries may be ambiguous or imprecise.

A major source of ambiguity arises from the systematic use of \texttt{LIMIT} clauses without \texttt{ORDER BY}. 
While \texttt{LIMIT} is necessary to keep query results and provenance expressions manageable, it induces non-deterministic semantics, 
as the returned tuples represent an arbitrary subset rather than ranked or semantically “top” results. 
This often leads NL translations to hallucinate notions such as “top”, “best”, or “most recent”, which are not justified by the SQL query.
Introducing \texttt{ORDER BY} is not an easy solution, as the query generator has no access to data distribution or domain semantics, 
and the language model does not observe the ordered context that would justify such constraints.

Additional issues come from set operations such as \texttt{UNION}, which remove duplicates by definition and therefore make the final cardinality 
of the result unpredictable, even when subqueries are bounded by \texttt{LIMIT}. 
Furthermore, the SQLSmith-based query generator frequently produces syntactically valid but semantically weak predicates (e.g., \texttt{IS NOT NULL} 
on primary-key-like attributes), which are difficult to translate faithfully into NL.

Given these considerations, we adopt a `curation` strategy. 
\begin{itemize}
    \item To mitigate the limitations introduced by \texttt{LIMIT}, 
    we propose a data curation strategy based on provenance-driven database recomposition. 
    This approach aims to construct a smaller but representative dataset that allows queries to be executed without \texttt{LIMIT}, 
    while keeping outputs and provenance manageable and semantically consistent.
\end{itemize}
\paragraph{Provenance-driven dataset recomposition}
The following procedure describes the proposed workflow for curating a database using provenance information, enabling the removal of the \texttt{LIMIT} clause
in a second generation of the dataset.

\begin{algorithm}[H]
\caption{Provenance-based Dataset Curation}
\label{alg:prov-curation}
\DontPrintSemicolon
\KwIn{Original database $D$, query generator $G$}
\KwOut{Curated database $D'$, updated query results and provenance}
\BlankLine

Generate a set of SQL queries $Q = \{q_1, \dots, q_n\}$ from $D$ using $G$, each including a \texttt{LIMIT} clause\;

\ForEach{$q_i \in Q$}{
    Execute $q_i$ on $D$ using ProvSQL, obtaining result $R_i$ and provenance $P_i$\;
}

Initialize an empty set of tuples $T_{\text{relevant}} \leftarrow \emptyset$\;

Extract all tuples referenced at least once in any provenance expression $P_i$ and add them to $T_{\text{relevant}}$\;

Construct a reduced database $D'$ containing only tuples in $T_{\text{relevant}}$\;

Re-execute the same set of queries $Q$ on $D'$ after removing all \texttt{LIMIT} clauses, collecting new results and provenance\;

\Return{$D'$, updated results, and provenance}\;
\end{algorithm}



\section{Data Pipeline}
The construction process merges three primary sources of information:
\begin{enumerate}
    \item \textbf{SQL queries}: SQL queries generated using a customized version of the fuzzy random generator sql smith. This has been adapted to produce queries more adapted for our task and for the execution with the provsql tool.
    \item \textbf{Provenance Data}: SQL queries executed with provenance computation (using \texttt{provsql}), providing the ground truth tuples and their corresponding why provenance sets.
    \item \textbf{Natural Language (NL) Queries}: NL descriptions of the SQL queries generated using llama3.3-latest : 70.6B.
    \item \textbf{Context Data}: The actual rows from the source database tables required to answer the query (extracted from the provenance expressions).
\end{enumerate}

\section{Negative Samples Generation (DPO)}
A critical component of this dataset is the generation of \textbf{rejected samples} for Direct Preference Optimization (DPO). Unlike standard SFT (Supervised Fine-Tuning) which only uses correct examples, DPO requires pairs of (chosen, rejected) outputs to teach the model to distinguish between valid and invalid provenance.

\subsection{Mutation Strategies}
The negative samples are generated by applying a single, controlled mutation to the correct provenance of a randomly selected tuple in the output. We implement five mutation modes to cover common errors:

\begin{itemize}
    \item \textbf{Add Token (Witness Set Extension):} Adds a random row identifier from the context to an existing witness set. This teaches the model not to include irrelevant rows.
    
    Example: [["circuits\_2","races\_19"]] -> 
    
    [["circuits\_2","races\_19","drivers\_11"]]
    \item \textbf{Remove Token (Witness Set Reduction):} Reduces a witness set to a single token. This helps the model understand that multiple rows are often simultaneously necessary (conjunction).
    Example: [["circuits\_2","races\_19"]] -> 
    
    [["circuits\_2"]]
    \item \textbf{Add Set (False Alternative):} Adds a new singleton witness set. This creates a "false alternative" explanation for the result.
    
    Example: [["circuits\_2","races\_19"]] -> 
    
    [["circuits\_2","races\_19"],["drivers\_8"]]
    \item \textbf{Remove Set (Missing Explanation):} Removes one of the witness sets (only if multiple exist). This teaches the model that provenance must be complete.
    
    Example: [["circuits\_2","races\_19"],["drivers\_8"]] -> 
    
    [["circuits\_2","races\_19"]]
    \item \textbf{Replace Token (Substitution):} Replaces a row identifier with another one from the same table. This maintains the schema validity but invalidates the provenance.
    
     Example: ["constructor\_standings\_33","races\_21"] -> 
     
     ["constructor\_standings\_34","races\_21"]
\end{itemize}



\subsection{Improving the Construction of t Fine-Tuning Dataset with Negative Pairs}

Input files:

\begin{itemize}
    \item \textbf{Provenance-enriched query results} (\texttt{--prov-jsonl}):  
    A JSONL file containing SQL queries, their execution results, and associated Why-provenance information.
    
    \item \textbf{Natural language queries} (\texttt{--nl-file}):  
    A JSON or JSONL file mapping query identifiers to their corresponding natural language questions.
    
    \item \textbf{Context data} (\texttt{--context-jsonl}):  
    A JSONL file containing the table rows used as evidence, indexed by query identifier.
\end{itemize}

Each query is identified by an integer ID, which is used to align SQL, natural language, and context data.

\subsubsection{Preprocessing and Filtering}

For each candidate query, the script performs the following preprocessing steps:

\begin{enumerate}
    \item \textbf{SQL cleaning}:  
    SQL comments and provenance-specific function calls are removed to avoid noise introduction into the prompt.
    
    \item \textbf{Context cleaning}:  
    Internal provenance metadata (e.g., \texttt{provsql} fields) are removed from the context rows, leaving only raw attribute values.
    
    \item \textbf{Metadata extraction}:  
    Query-level metadata (number of joins, aggregates, set operators, and negation) are parsed from structured comments embedded in the SQL.
\end{enumerate}

Queries are discarded if any of the following conditions hold:
\begin{itemize}
    \item Missing metadata
    \item Missing natural language question
    \item Missing context data
    \item Empty result set
\end{itemize}

\subsubsection{Query Categorization}

Each remaining query is assigned to one of five categories based on its metadata:

\begin{itemize}
    \item \texttt{easy\_no\_join}: no joins, no aggregates, no set operators
    \item \texttt{medium\_join}: one or more joins, no aggregates
    \item \texttt{has\_aggr}: aggregate queries
    \item \texttt{has\_union}: queries containing UNION only
    \item \texttt{has\_all}: queries containing multiple advanced operators (UNION, EXCEPT)
\end{itemize}

This categorization enables balanced dataset construction and categorized analysis during training and evaluation.

\subsubsection{Prompt Construction}

For each selected query, a prompt is built using a fixed instruction template. The prompt contains:

\begin{itemize}
    \item A strict instruction requiring \emph{only valid JSON output}
    \item The SQL query (used as the question)
    \item The cleaned context data, serialized as JSON
\end{itemize}

The expected output format is a JSON array of objects, each containing:
\begin{itemize}
    \item \texttt{result}: one output tuple
    \item \texttt{provenance}: a Why[X] provenance expression represented as a list of lists.
\end{itemize}

\subsubsection{Generation of Negative Outputs}

To enable preference-based fine-tuning, the script generates a \emph{rejected} (negative) output for each correct (\emph{chosen}) output.

Negative outputs are produced by applying multiple randomized edits to the provenance annotations while keeping the result tuples unchanged.
The edits are designed to mimic realistic model errors observed in practice. Examples include:

\begin{itemize}
    \item Replacing provenance tokens with identifiers from the same or different tables
    \item Adding or removing tokens from a witness set
    \item Adding or removing entire witness sets
    \item Duplicating table prefixes or row indices (e.g., \texttt{nation\_1} $\rightarrow$ \texttt{nation\_nation\_1})
    \item Flattening multiple singleton witness sets into a single incorrect set
    \item Rarely, merging the provenance of two distinct result tuples
\end{itemize}

Each negative example typically applies multiple edits across different tuples, increasing its difficulty and diversity.

The applied corruption strategy is recorded using a \texttt{negative\_mode} label for later analysis.

\subsubsection{Output Format}

For each category, the script produces a JSONL file where each line contains:

\begin{itemize}
    \item \texttt{id}: query identifier
    \item \texttt{prompt}: the full model input prompt
    \item \texttt{chosen}: the correct output (JSON-serialized)
    \item \texttt{rejected}: the corrupted output (JSON-serialized)
    \item \texttt{negative\_mode}: description of the applied corruption
\end{itemize}

Additionally, a global statistics file is generated, reporting:
\begin{itemize}
    \item Number of selected queries per category
    \item Distribution of query structural types
    \item Frequency of each negative corruption mode
\end{itemize}

\subsubsection{Purpose and Benefits}

The resulting dataset is directly usable for DPO-style fine-tuning and is particularly suited for provenance-aware question answering systems over relational data.
It can also be adapted for standard supervised fine-tuning by ignoring the \texttt{rejected} field, providing a rich source of provenance-annotated examples for various training paradigms.

\section{Adding bad format records}

To further enhance the model's reliability, we incorporate a second category of negative samples focused on \textbf{json integrity} and \textbf{output format}. While the primary dataset focuses on logical provenance errors, this augmentation step teaches the model to resist common LLM errors, such as adding conversational sentences or deviating from the specified JSON structure.

\subsection{Methodology}
We employ an LLM-in-the-loop approach (using \texttt{Ollama}) to generate "bad-format" rejected samples. By appending adversarial suffixes to the original prompts, we force the generator to produce outputs that violate the schema in specific, weighted ways:

\begin{table}[h]
\centering
\begin{tabular}{@{}llp{6cm}@{}}
\toprule
\textbf{Attack Category} & \textbf{Weight} & \textbf{Description} \\ \midrule
\texttt{extra\_keys} & 12.5\% & Adds unauthorized keys (e.g., \texttt{"explain"}) to the objects. \\
\texttt{wrong\_key\_name} & 12.5\% & Renames \texttt{"provenance"} to \texttt{"prov"}, testing key-name precision. \\
\texttt{wrong\_schema} & 12.5\% & Flattens the provenance list or converts it to a single string. \\
\texttt{bad\_id\_format} & 12.5\% & Uses incorrect separators (e.g., \texttt{table-id} vs \texttt{table\_id}). \\
\texttt{invalid\_json} & 37.5\% & Forces syntax errors like unclosed brackets or missing commas. \\ \bottomrule
\end{tabular}
\caption{Adversarial strategies for format-based rejected samples.}
\end{table}



\subsection{Adversarial Filtering Logic}
The generation process follows a strict validation loop to ensure the "rejected" sample is truly broken before it is added to the dataset:
\begin{enumerate}
    \item \textbf{JSON Extraction}: The script attempts to isolate a JSON array from the LLM's raw response, effectively removing any conversational prefixes.
    \item \textbf{Schema Validation}: The isolated text is passed through a validator (\texttt{is\_valid\_output\_schema}) which checks for:
        \begin{itemize}
            \item Valid JSON syntax.
            \item Correct top-level type (Array).
            \item Exact key matching (\texttt{result} and \texttt{provenance}).
            \item Regex-based validation of provenance identifiers 
            (\texttt{<table\_name>\_<row\_number>}).
        \end{itemize}
    \item \textbf{Negative Selection}: A sample is only accepted if it \textbf{fails} one of these checks, ensuring that the DPO "rejected" field is objectively incorrect according to the task instructions. At the end 100 samples have been added for each dataset (300 in total).
\end{enumerate}

\section{Dataset Partitioning and Stratification}
The final stage of the pipeline involves shuffling and splitting the merged dataset into training, validation, and test sets. To ensure that the model generalizes well across different types of queries and provenance from different data source, we implement a \textbf{splitting strategy}.

\subsection{Tag-Based Stratification}
Each record in the dataset is identified by a unique ID that includes a "tag" suffix, refering to the source dataset(e.g., \texttt{101\_t}, \texttt{102\_rs}). The splitting script uses these tags to maintain the distribution of samples:

\begin{enumerate}
    \item \textbf{Grouping}: Data is grouped by its categorical tag.
    \item \textbf{Local Shuffling}: Within each group, samples are shuffled using a fixed seed (\texttt{42}) to ensure reproducibility.
    \item \textbf{Proportional Allocation}: Samples are allocated to the \textit{Train}, \textit{Validation}, and \textit{Test} sets based on predefined ratios (default: 85\% / 10\% / 5\%).
    \item \textbf{Global Re-shuffling}: Once the sets are formed, they are shuffled globally to prevent the model from learning biases based on the sequence of query types.
\end{enumerate}


\section{Cleaning Dataset}
Before proceeding to training, the dataset is cleaned and adapted to the template for the fine tuning. 

\subsection{Token-Based Filtering}
We use the \texttt{Meta-Llama-3-8B-Instruct} tokenizer to calculate the exact length of each prompt-response pair. This is critical for preventing Out-Of-Memory (OOM) errors during fine-tuning.

\begin{itemize}
    \item \textbf{Prompt Capping}: Examples with a prompt exceeding 2048 tokens are discarded.
    \item \textbf{Pair Capping}: The total length of the (Prompt + Chosen) or (Prompt + Rejected) sequence is capped at 4096 tokens.
    \item \textbf{Key Dropping}: To further reduce token counts, irrelevant database metadata (e.g., \texttt{comment}, \texttt{text}) are recursively removed from the JSON context without affecting the logical integrity of the query.
\end{itemize}

The script utilizes the \texttt{DPOTrainer} from the \textit{TRL} library. A crucial stability choice is the use of \textbf{Bfloat16} precision and the avoidance of 4-bit quantization where memory allows, ensuring higher gradient precision during the preference learning phase.

\section{Model Deployment: From Adapters to Ollama}
Once training is complete, the process yields a \textbf{PEFT Adapter}. This adapter contains the "delta" weights that transform the base Llama-3 model into a provenance-aware assistant.

To facilitate testing and local usage, the adapter can be integrated into \textbf{Ollama} using a custom \texttt{Modelfile}:
\begin{enumerate}
    \item \textbf{Base}: Use the original Llama-3-8B-Instruct.
    \item \textbf{Adapter}: Link the path to the trained LoRA weights.
    \item \textbf{Template}: Ensure the prompt template matches the one used during training.
\end{enumerate}
